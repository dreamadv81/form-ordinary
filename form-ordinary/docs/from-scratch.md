# Форма с нуля: `new`, `generate` без `--form`, `remove_attribute`

Часть навыка `form-ordinary`; навигатор и таблица «Тема → файл» — в `SKILL.md`. Документ ведёт от пустой формы до готовой одной цепочкой: `new` кладёт заготовку, `generate` строит по описанию то, что умеет словарь блоков, `edit` добавляет остальное. Сквозной пример — одна форма обработки; каждая команда и каждый входной файл примера выполняются дословно (их прогоняет проверка навыка).

**Метаданных команды не заводят.** Форма объекта (справочника, документа, обработки, отчёта) — часть конфигурации: сначала форму создают в конфигураторе (или берут существующую), навык пишет её содержимое. `new` создаёт файл формы, а не форму в конфигурации. Исключение по смыслу одно: у внешней обработки и внешнего отчёта формы в метаданных конфигурации нет, и тип основного реквизита берётся из корневого XML их выгрузки (`--root-xml`) либо задаётся GUID-ом (`--type-id`).

## Форма уже есть или новая

| у вас | с чего начать |
|---|---|
| готовый `form.frm`, `Form.bin`, каталог формы | `edit` по просьбе, `generate --form` — см. `SKILL.md` |
| формы нет: внешняя обработка | `frm_json.py new processing -o form.frm --root-xml <Имя>.xml` (либо `--type-id <GUID>`): основной реквизит `ОбработкаОбъект` с типом Object обработки |
| формы нет: внешний отчёт | `frm_json.py new report -o form.frm --root-xml <Имя>.xml` (либо `--type-id <GUID>`; отчёт конфигурации — `--object Отчет.Имя --config <каталог выгрузки>`): основной реквизит `ОтчетОбъект` с типом Object отчёта |
| формы нет: форма-диалог без основного реквизита | `frm_json.py new processing -o form.frm --dialog` |
| форма документа или справочника, выгрузки конфигурации нет, а GUID типа основного реквизита известен | `frm_json.py new document.item -o form.frm --type-id <GUID>` (`catalog.item`, `document.list`, `catalog.list` — так же): заготовка та же, что с выгрузкой, без реквизитов объекта; GUID выдаёт конфигурация, придуманный GUID форму в конфигурации не свяжет с объектом |
| форма объекта создана в конфигураторе и пуста | выгрузите её (`form.frm` рядом с `Form.bin`) и стройте `generate --form` по ней; если выгрузить нечем, `new <вид> --object … --config …` собирает пустую форму того же вида по выгрузке конфигурации, и её содержимое записывают в форму конфигурации |

## `new`: пустая заготовка

```
frm_json.py new <вид> -o form.frm [--title Текст] [--size ШxВ] [--object Вид.Имя --config <каталог выгрузки>] [--type-id GUID] [--root-xml <Имя>.xml] [--dialog] [--bsl-out form.bsl] [--overwrite]
```

Заготовка — форма, которую создаёт конструктор платформы 8.3.27, без содержимого: панели формы и основной реквизит. Кнопок с обработчиками в ней нет; кнопки панелей — стандартные действия платформы. Рядом пишется пустой `form.bsl` (одна метка порядка байтов, как у выгрузки платформы); существующий `form.bsl` команда не трогает, существующий файл `-o` без `--overwrite` не затирает; каталоги для `-o` создаются.

| вид | основной реквизит | что в заготовке |
|---|---|---|
| `processing` с `--root-xml <Имя>.xml` (внешняя обработка) | `ОбработкаОбъект`, тип — `Object` обработки из её корневого XML | панель `ДействияФормы` (сверху), панель `ОсновныеДействияФормы` (снизу) с кнопкой «Закрыть» |
| `processing` с `--type-id GUID` | `ОбработкаОбъект`, тип — заданный GUID (TypeId из `xr:GeneratedType category="Object"` обработки) | то же |
| `processing` с `--object Обработка.Имя --config` | `ОбработкаОбъект`, тип — `Object` этой обработки из выгрузки конфигурации | то же |
| `processing --dialog` | нет; реквизитов формы нет | то же |
| `processing` без этих ключей | — | отказ: источник типа не назван |
| `report` с `--root-xml <Имя>.xml` (внешний отчёт), `--type-id GUID` или `--object Отчет.Имя --config` | `ОтчетОбъект`, тип — `Object` отчёта; тип значения формы — тип формы отчёта | панель `ДействияФормы` (сверху), панель `ОсновныеДействияФормы` (снизу) с кнопкой «Закрыть» (кнопки «Сформировать» нет: она вызывает процедуру формы, которой в пустом модуле нет) |
| `report` без этих ключей, `report --dialog` | — | отказ: источник типа не назван; формы-диалога отчёта нет |
| `catalog.item` | `СправочникОбъект`, тип — `Object` справочника | те же панели; нижняя — с кнопками «ОК», «Записать», «Закрыть» |
| `document.item` | `ДокументОбъект`, тип — `Object` документа | то же |
| `catalog.list` | `СправочникСписок`, тип — `List` справочника | панель `ДействияФормы` и табличное поле списка со стандартными колонками (`Картинка`, `Код`, `Наименование`) |
| `document.list` | `ДокументСписок`, тип — `List` документа | то же, колонки `Картинка`, `Дата`, `Номер` |

* Форме справочника, документа и списка нужны `--object` (`Справочник.Имя`, `Документ.Имя`) и `--config` (каталог выгрузки XML: `Catalogs/`, `Documents/`, `DataProcessors/`) либо вместо них `--type-id` (ниже): основной реквизит несёт тип объекта, и без объекта заготовки нет — отказ называет, чего не хватило. `--type-id` задаёт тип основного реквизита GUID-ом, когда выгрузки нет, а тип известен: Object обработки, справочника или документа, List списка; вместе с `--object` не берётся. Для формы справочника или документа без выгрузки это единственный путь; нижняя панель документа и справочника в заготовке уже стоит (ОК, Записать, Закрыть), а на форме другого вида её ставит `add_element` с `bar_for: "form_bottom"` и ключом `kind` (`docs/edit-buttons.md`).
* **Нижняя панель формы документа или справочника** на заготовке `processing` (основной реквизит — объект обработки, а не документа или справочника) ставится одним шагом: `add_element` с `template: "CommandBar"`, `bar_for: "form_bottom"`, `kind: "document.item"` (или `catalog.item`) и `replace: true` — прежняя нижняя панель убирается. Порядок кнопок — `move_button` и `before` / `after` / `index` у `add_button`, «Провести» в нижнюю панель по умолчанию не ставят: оно в верхней панели документа, где его ставит автозаполнение (`docs/edit-buttons.md`, раздел «Место кнопки, нижняя панель формы, стандартные действия»). Кнопка «ОК» записана по умолчанию (`default_button`) и не жирная: так у конструктора, жирной бывает только кнопка по умолчанию со своей процедурой.
* **Форма обработки несёт основной реквизит `ОбработкаОбъект` с типом Object обработки, и источник типа называют всегда**: `--root-xml`, `--type-id` или `--object` с `--config`. Без основного реквизита модуль формы не видит реквизитов и экспортных методов модуля обработки, и вызов, например, `НоваяТаблицаДокументов()` при открытии формы не компилируется. Команда без источника типа отказывает и называет три выхода. `--root-xml` читает корневой XML выгрузки внешней обработки (`<Имя>.xml` рядом с каталогом `<Имя>/`): корень `ExternalDataProcessor`, тип — `InternalInfo/xr:GeneratedType category="Object"`, заголовок формы — по синониму обработки (`Обработка  Синоним`, как у `--object`). Корень `ExternalReport` виду `processing` не подходит — отказ называет вид `report`. `--type-id` берёт GUID оттуда же (`xr:TypeId` этого `GeneratedType`). Обработка, названная в `--object`, но не найденная в выгрузке, — тоже отказ: внешняя обработка в конфигурации не лежит, её тип даёт корневой XML. Ключи `--root-xml`, `--type-id`, `--object`/`--config` и `--dialog` друг с другом не берутся. **`--dialog`** — форма без основного реквизита и без реквизитов формы (диалог, которому модуль обработки не нужен): модуль такой формы не видит реквизитов и экспортных методов модуля обработки, отчёт `new` называет это строкой. Форма с основным реквизитом получает такие же панели; разница в одной строке реквизитов формы.
* **Форма отчёта (`new report`)** собирается по форме внешнего отчёта конструктора: те же две панели; нижняя несёт кнопку «Закрыть». Конструктор ставит в нижнюю панель ещё «Сформировать» и разделитель, но «Сформировать» вызывает процедуру формы `КнопкаСформироватьНажатие`, а модуль новой формы пуст, поэтому кнопка не ставится — как у заготовки обработки без «Выполнить»; кнопку со своей процедурой добавляют `add_button` и текст модуля; основной реквизит `ОтчетОбъект` и тип значения формы — тип формы отчёта. Источник типа основного реквизита называют всегда, как у обработки: `--root-xml <Имя>.xml` (корень `ExternalReport`; корень `ExternalDataProcessor` отказывает и называет вид `processing`), `--type-id` (TypeId `GeneratedType category="Object"` отчёта) или `--object Отчет.Имя --config <каталог выгрузки>` (каталог `Reports/` в выгрузке: тип значения формы, основной реквизит и привязки у формы отчёта конфигурации того же вида, что у внешнего; в предприятии такая форма не проверялась, а нижняя панель конструктора у отчёта конфигурации иная — «ОК»/«Отмена» либо без панели, заготовка несёт панель внешнего отчёта). Заголовок без `--title` — `Отчет  Синоним`. Формы-диалога отчёта нет: `--dialog` отказывает (такая форма в выгрузках конфигураций единична, и тип значения формы у неё иной).
* Размер по умолчанию 400×300; `--size 560x480` ставит другой, панели встают по краям. Минимум — ширина 100 и высота 60 (у списка — своя, отказ называет числа).
* Заголовок без `--title` — по синониму объекта, как у конструктора («Товары», «Справочник Товары», «Документы Заказ», «Обработка  Загрузка»), без объекта — «Форма». Это значение свойства заголовка; автозаголовок формы платформа показывает сама.
* GUID панелей и их кнопок выдаются заново при каждом вызове: у каждой формы они свои. Таблицы списка `new` не перестраивает: у иерархического справочника в заготовке нет дерева групп.
* Форма справочника или документа получает панели и основной реквизит, **полей и табличных частей объекта в ней нет**: их ставит `generate` по описанию или `edit` (`add-field` — реквизиты шапки одним вызовом).
* `-o …/Ext/form.frm` рядом с `Form.bin` — и `Form.bin` соберётся (`docs/formbin.md`); `-o Form.bin` и каталог отказывают.

## `generate` без `--form`

```
frm_json.py generate описание.json -o form.frm [--config <каталог выгрузки>] [--type-id GUID | --root-xml <Имя>.xml | --dialog]
```

Вид и объект берутся из описания (`kind`, `object`); исходной формой служит заготовка `new` того же вида. Отчёт начинается строкой «Исходная форма не названа: взята заготовка навыка …»; бережный режим на заготовке не включается (беречь нечего), раскладка полная. Повтор по тому же описанию даёт тот же файл байт в байт (GUID панелей выдаются от суммы описания), и команда отвечает «Ничего не изменилось». Нужная выгрузка — та же, что у `new`: у справочника, документа и списка обязательна. `--root-xml` у `generate` работает и без заготовки, с `--form` (`docs/generate.md`, абзац «Внешняя обработка»), и даёт полям привязку к реквизитам и табличным частям внешней обработки; сквозной путь от формы до сборки `.epf` — `docs/epf.md`, раздел «Форма внешней обработки с привязками». У вида `processing` (и у описания с объектом-отчётом) источник типа основного реквизита называют так же, как у `new`: `--type-id` или `--root-xml` (либо `--config`, где есть обработка из `object` описания), либо `--dialog` для формы без основного реквизита; без источника — отказ. С `--form` эти три ключа отказывают: тип основного реквизита берётся из исходной формы. Форма, которую вы правили после генерации, без `--overwrite` не затирается (`docs/generate.md`).

## `remove_attribute`

`{"op": "remove_attribute", "name": "Причина"}` убирает реквизит формы — обратная к `add_attribute`. Отказ словами, пока на реквизит что-то ссылается: он основной; к нему привязаны элементы (названы по именам и индексам); на него указывает «Связь по типу»; он назван в «Сохраняемых значениях». Счётчик `next_id` возвращается, если убран последний выданный номер: пара `add_attribute` → `remove_attribute` даёт исходную форму байт в байт. Подробности — `docs/edit-module-data.md`.

`add_attribute` работает и у заготовки внешней обработки, где реквизитов нет: тип задаётся описателем `pattern` (донора нет), первая строка собирается по самому частому виду строки таких форм.

## Сквозной пример: форма обработки «Параметры выпуска»

Форма: пары «надпись + поле» (строка, дата), флажок, закладки «Основное» и «Состав»; на первой — многострочное поле, поле выбора со списком и поле даты; на второй — группа переключателей, таблица с панелью и поле под ней; внизу панель формы. Размер 560×480.

**Шаг 1. Заготовка.** Внешняя обработка; тип основного реквизита — TypeId из `InternalInfo/xr:GeneratedType category="Object"` корневого XML выгрузки обработки (в примере — GUID учебной обработки; своего GUID у обработки не угадать):

```
frm_json.py new processing -o работа/01.frm --title "Параметры выпуска" --size 560x480 --type-id 54e4e335-8098-40a1-a117-4ddfb3ddfab3
```

```text
Заготовка: форма конструктора вида «processing»
основной реквизит формы — тип 54e4e335-8098-40a1-a117-4ddfb3ddfab3, заданный явно
размер 560×480, заголовок «Параметры выпуска»; модуль формы пуст
Записано: работа/01.frm
Записано: работа/form.bsl
```

В `работа/` лежат `01.frm` (две панели, основной реквизит `ОбработкаОбъект`) и пустой `form.bsl` (модуль всегда называется `form.bsl`). Папку создаёт `new`.

**Шаг 2. Описание: почти вся форма.** `generate` ставит пары, флажок, закладки, панели формы, поле выбора (`choice_list`), многострочное поле (`multi_line`), группу переключателей (блок `radio`, реквизит группы блок заводит сам), таблицу значений с панелью и поля под ней; реквизиты формы объявляет ключ `attributes`, поле на реквизит формы — `"source": "form"`; состав даты называют словом (`"date": "Date"`) или буквой (`"date_fractions": "D"`) — одинаково у реквизита и у колонки. Каждая закладка должна нести хотя бы один блок. Файл `описание.json`:

```json
{"kind": "processing", "object": "Обработка.ПараметрыВыпуска", "title": "Параметры выпуска", "size": [560, 480],
 "attributes": [{"name": "Наименование", "type": "string", "length": 50},
                {"name": "Мастер", "type": "string", "length": 30},
                {"name": "НачалоВыпуска", "type": "date", "date": "Date"},
                {"name": "Срочный", "type": "boolean"},
                {"name": "Комментарий", "type": "string"},
                {"name": "Основание", "type": "string", "length": 30},
                {"name": "СрокПередачи", "type": "date", "date_fractions": "D"},
                {"name": "Итого", "type": "number", "digits": 12, "fraction": 2},
                {"name": "Состав", "type": "ValueTable"}],
 "blocks": [{"command_bar": "top"},
            {"fields": [{"data": "Наименование", "source": "form"}, {"data": "Мастер", "source": "form"},
                        {"data": "НачалоВыпуска", "source": "form"}, {"data": "Срочный", "source": "form"}], "columns": 2},
            {"tabs": [{"page": "Основное", "blocks": [
                         {"fields": [{"data": "Комментарий", "source": "form", "multi_line": true}]},
                         {"fields": [{"data": "Основание", "source": "form", "choice_list": ["Плановая", "Заказ клиента", "Ремонт"]},
                                     {"data": "СрокПередачи", "source": "form", "caption": "Срок:"}]}]},
                      {"page": "Состав", "blocks": [
                         {"radio": "ВидВыпуска", "caption": "Вид выпуска", "options": ["Плановый", "Срочный"]},
                         {"table": "Состав", "source": "form",
                          "columns": [{"name": "Номенклатура", "header": "Номенклатура", "width": 300},
                                      {"name": "Количество", "header": "Количество", "width": 90, "align": "Right", "format": "ЧДЦ=3"}]},
                         {"fields": [{"data": "Итого", "source": "form"}]}]}]},
            {"command_bar": "bottom"}]}
```

```
frm_json.py generate описание.json --form работа/01.frm -o работа/02.frm --render работа/02.svg
```

```text
Режим: полная раскладка
Записано: работа/02.frm
```

Без `--form` та же команда берёт заготовку сама (раздел «`generate` без `--form`»; ключ типа `--type-id` тот же); шаг 1 нужен, когда заготовку хотят увидеть или править `edit` до генерации. Панель закладок получила имя `Панель1`, страницы — `Страница1` и `Страница2` (их заголовки — «Основное» и «Состав»); имена элементов даёт правило конструктора: `НадписьМастер` и `Мастер`, `Срочный`.

**Шаг 3. Правка: то, чего словарь не выражает.** Второй закладке нужен другой заголовок, а словарь называет страницы только в `tabs`; свойство ставит `set_property`. Файл `ops.json`:

```json
[
 {"op": "set_property", "element": "Панель1", "page": 1, "name": "caption", "value": "Состав выпуска"}
]
```

```
frm_json.py edit работа/02.frm --ops ops.json -o работа/03.frm --render работа/03.svg
```

```text
Записано: работа/03.frm
Масштаб правки: затронуто 1 из 16 существующих элементов
```

**Шаг 4. Проверка.**

```
frm_json.py validate работа/03.frm
frm_json.py lint работа/03.frm --kind processing
frm_json.py anchors-check работа/03.frm
```

```text
Итог: замечаний 0
поломок привязок нет
```

`validate` печатает предупреждения уровня 2 — их три у поля выбора со списком («в блоке детей 1, а корпус видел длину 3») и три у панели закладок; это замечания о длине блоков, отказом они не являются. Каждое называет причину словами: такую длину записывает платформа (список выбора без представлений, список страниц панели с двумя страницами), запись совпадает с записью платформы, на работу формы не влияет. Саму форму смотрят на картинке: `frm_json.py render работа/03.frm -o работа/03.png`, вторую закладку — `--shown Панель1=1`. Форму откройте в конфигураторе и запустите в предприятии: пересохранение платформой не доказывает, что форма работает.

## Сдвинуть панель закладок и поставить соседа

`generate` кладёт панель закладок на всю ширину; дерево слева ставят после: панель с детьми переносится и сужается одной операцией, дети идут по своим правилам на всех страницах.

Операции перечня `ops.json`, по порядку:

1. `{"op": "add_attribute", "name": "ДеревоЗаданий", "pattern": {"mark": "Pattern", "types": [{"kind": "ValueTree"}]}}` — реквизит дерева;
2. `{"op": "move_element", "name": "Панель1", "box": [370, 32, 722, 600], "anchor": "keep"}` — панель вправо и уже, дети идут за краями;
3. `{"op": "add_element", "template": "TreeBox", "name": "ДеревоЗаданий", "attribute": "ДеревоЗаданий", "box": [8, 32, 350, 600], "anchor": {"h": "left", "v": "stretch"}, "columns": [{"name": "Задание", "header": "Задание", "type": {"kind": "S", "length": 100}, "width": 220}]}` — дерево слева;
4. `{"op": "add_element", "template": "Splitter", "name": "Разделитель1", "between": ["ДеревоЗаданий", "Панель1"]}` — разделитель между ними.

`anchor: "keep"` у панели оставляет её правила (растягивается вместе с окном). Рамку с полями внутри сдвигают одной операцией: `{"op": "move_element", "name": "РамкаШапки", "by": [0, 120], "with_contents": true, "anchor": "keep"}` (рамка у нижнего края — `"anchor": {"h": "stretch", "v": "bottom"}` и `"contents_anchor": {"v": "bottom"}`); правила — `docs/edit-rules.md`, раздел `move_element`.

## Две таблицы с разделителем

Список групп слева и список позиций справа, между ними разделитель, над каждой таблицей панель с автозаполнением (форма 780×520 после `new processing --dialog`). Файл `две-таблицы.json`:

его место показывает `frm_json.py layout form.frm --grow 200x100`. `anchors-check` на такой форме печатает одну справку «как у платформы» (правило нижней панели и разделителя на

## Входные форматы, о которые спотыкаются

* **Страница панели.** У `add_element`, `move_element`, `set_tab_order`, `reparent`, `set_property` (страница панели) ключ `page` — **номер страницы с нуля** (`"page": 1` — вторая) **или её имя** (`"page": "Страница2"`, как у любой страницы, созданной платформой или `generate`; заголовок страницей не называет). Имя должно называть ровно одну страницу; несуществующее имя и номер вне страниц отказывают с перечнем. `holder` — имя панели. Имена страниц называет отказ.
* **Координаты `box` на странице панели.** У вложенного в панель элемента `box` отсчитывается от левого верха **области страницы** (под полосой закладок, внутри рамки панели), а не от формы: у панели в (8, 56) с закладками «Сверху» начало лежит в (9, 75) формы. Отчёт `edit --render` печатает оба набора: `Панель1/Новая (19,115,100,19) [box на странице 0: (10,40,100,19)]` — в скобках координаты формы, в квадратных — то, что вписывают в `box` (`docs/edit-rules.md`, «`move_element`»).
* **Вторая страница панели.** `{"op": "add_page", "panel": "Панель1", "name": "Страница3", "caption": "Итоги"}` (`docs/form-pages.md`, раздел «`add_page` — страница панели»); страницу первой панели `generate` называет `Страница1`, переименования страницы нет — заголовок закладки меняет `{"op": "set_property", "element": "Панель1", "page": 0, "name": "caption", "value": "Основное"}`.
* **Группа переключателей.** Реквизит группы — число с одной цифрой (`{"kind": "N", "digits": 1, "fraction_digits": 0, "nonnegative": true}`). Данные получает только **первый** переключатель группы: `first_in_group`, `bind` с `copy_type`. Остальные получают выбираемое значение `set_property selected_value`: голое число `1` приводится к объекту `{"kind": "N", "value": 1}` по типу реквизита группы (тип первого переключателя); группа без типа или значение другого вида отказывают с примером объекта, готовый объект принимается как есть. Рамка группы — обычный `GroupBox`, переключатели ставятся поверх неё с теми же `holder` и `page`: рамка не их родитель (у `GroupBox` вложенных нет), принадлежность группе задают только порядок обхода и `first_in_group`, поэтому переключатели группы идут в порядке обхода подряд.
* **Тип даты.** Описатель — `{"kind": "D", "date": "Date"}` — дата (`"Time"` — время, `"DateTime"` — дата и время; те же слова, что в ключе `attributes` описания `generate`); краткая запись равна `{"kind": "D", "date_fractions": "D"}` (`"T"` — время; без ключа — дата и время). Поле даты привязывают с `copy_type`, кнопку календаря включает `choice_button`; `add_pair` делает всё это одним вызовом (ниже).
* **Поле на реквизит формы.** `bind` с `copy_type: true` переносит тип реквизита в поле ввода, флажок и переключатель. Поле выбора (`ComboBox`) `copy_type` не принимает: его привязывают без ключа.
* **Надпись, поле и привязка одним вызовом.** `{"op": "add_pair", "attribute": "СрокВыпуска", "caption": "Срок:", "holder": "Панель1", "page": 0, "after": "Причина", "kind": "processing"}` ставит надпись и поле на реквизит формы по соседям (после пары, названной в `after`), выравнивает поле по строке надписи, берёт тип и привязку у реквизита, у даты — ширину и кнопку календаря; `kind` нужен, когда на форме нет двух смежных строк полей. Булев реквизит ставится флажком. Реквизит формы должен уже быть (`add_attribute`).
* **Надпись на реквизит.** Надпись (`Label`) показывает значение реквизита формы, если её привязать: `{"op": "bind", "element": "Статус", "attribute": "Состояние"}` — без `copy_type` (у надписи описателя типа нет, переносить нечего). Привязка надписи встречается в формах конфигураций; в предприятии при проверке редактора не открывалась — отчёт говорит об этом словами.
* **Список выбора.** Ключ `choice_list` у `add_element` поля выбора (или `set_property` с `name: "choice_list"`): массив значений, каждое — строка либо `{"value": …, "presentation": …}` (`docs/edit-setprop.md`).
* **Таблица, дерево и список значений.** Реквизит формы такого типа называют по имени: `{"kind": "ValueTable"}` (таблица значений), `{"kind": "ValueTree"}` (дерево значений), `{"kind": "ValueList"}` (список значений); `decode` печатает их как `{"kind": "#", "value_type": "ValueTable"}`, в файле остаётся GUID типа. Табличное поле на таблицу значений — `add_element` с `template` `TableBox`, ключом `attribute` (реквизит; поле привязывается и приводится к его типу) и ключом `columns` (колонки: имя — оно же Данные, `header`, `width`, `align`, `format`; безымянную колонку шаблона операция снимает сама). Дерево — `template` `TreeBox` и реквизит `ValueTree`: первая колонка получает «Иерархию». **Тип колонки** — ключ `type` (`{"kind": "N", "digits": 15, "fraction": 3}`, `S`, `D`, `B`): колонки и их типы хранит форма, платформа создаёт их при открытии, и код таблицы только заполняет строки (колонку, которой в форме нет, код добавить может, но табличное поле её не показывает: чтобы её видеть, у поля нужна колонка с этими данными). Булева колонка — флажок: путь данных в «ДанныеФлажка», «Данные» пусты (иначе значение показывается текстом «Да»/«Нет»). У дерева хотя бы одна колонка — с «Иерархией» (по умолчанию первая), иначе дерево открывается плоской таблицей. Число и дату в ячейке показывает формат колонки: `"format": "ЧДЦ=3"`, `"format": "ДФ=dd.MM.yyyy"`. Список значений показывает поле списка: `add_element` с `template` `ListBox` и `bind` на реквизит `ValueList`. Табличного поля на список значений редактор не ставит (`docs/edit-columns.md`, раздел «Таблица значений и дерево значений на реквизит формы»).
* **Панель над таблицей.** `{"op": "add_element", "template": "CommandBar", "bar_for": "<таблица>"}` ставит панель с автозаполнением вплотную над таблицей, которая уже стоит на форме (x и ширина таблицы, высота 24, привязки по таблице, имя `КоманднаяПанель<N>`, источник действий — таблица): стандартные кнопки (Добавить, Изменить, Удалить, Вверх, Вниз…) ставит платформа, своими кнопками ставят только свои команды формы (с обработчиком в модуле). Место над таблицей должно быть свободно, иначе отказ называет мешающие элементы. Панель таблицы табличной части объекта `generate` ставит сам: блок `table` с ключом `bar` (`docs/generate.md`, `docs/edit-buttons.md`). Если панель уже стоит раньше таблицы, источник действий называет таблица ключом `action_bar` (имя панели) при постановке; вручную — `action_source` у панели или `set_action_source`.
* **Размер и привязки.** `move_element` без `anchor` пишет привязки «к себе»; чтобы сохранить правила, которые поставил `generate`, называют `"anchor": "keep"` (поле остаётся растягиваемым вместе с панелью).
* **Заготовка и `Form.bin`.** `new` пишет `form.frm`; в каталоге формы платформы с `Ext/Form.bin` назовите `-o …/Ext/form.frm`, тогда `Form.bin` соберётся.

## Чего пример и заготовка не делают

* Над таблицей значений стоит панель с автозаполнением, а в таблице нет строк: кнопки ставит платформа, содержимое приходит из кода.
* Заготовки собраны из форм конструктора платформы 8.3.27, а пример — операциями редактора по образцам форм; в предприятии заготовки и пример не открывались. Откройте форму в конфигураторе и запустите: пересохранение платформой не доказывает, что форма работает.
* Новые формы объектов в метаданные не попадают (см. начало документа).
