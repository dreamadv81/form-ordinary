# Кодек: устройство блоков

Часть навыка `form-ordinary`; навигатор и таблица «Тема → файл» — в `SKILL.md`. Документ описывает, как в файле формы и в JSON устроены кнопки и действия, наборы кнопок и их владельцы, дерево элементов, блок координат, данные и ссылки, варианты строения блоков, список выбора, меню кнопки, колонка с вложенным элементом, сжатие и шрифт.

Термины формата (подробно — `FORMAT.md`). **Счётный список** — счётчик, за которым идёт столько же блоков; в JSON это массив, счётчик отдельным полем не хранится. **Голова** блока — его начальные позиции до списков, **хвост** — позиции после них. **Родитель** элемента — панель или форма, на которой он лежит.

## Кнопка командной панели

Блок действий командной панели (`2/1/7`) состоит из головы в четыре позиции и двух счётных списков подряд, без хвоста: записей действий и наборов кнопок. Здесь в карте два вида отрезков:

* **Счётный список пар** (`CountedPairs`): набор кнопок записан как `{5, GUID, код, 0, счётчик, GUID, кнопка, GUID, кнопка, …, хвост}`. В JSON ключ пары лежит внутри объекта кнопки полем `id`; по нему кнопка связана со своим действием.
* **Отрезок по битам** (`Flagged`): в записи действия за словом флагов идёт по блоку на каждый поднятый бит — подсказка (2), пояснение (4), картинка (1), сочетание клавиш (8). Порядок блоков не совпадает с порядком масок: строки идут раньше картинки, картинка — раньше сочетания, а при обоих строковых битах первой лежит Подсказка, второй — Пояснение. Слово флагов в JSON отдельным полем не хранится: оно определяется набором присутствующих ключей.

**Подсказка, Пояснение, Картинка и СочетаниеКлавиш кнопки лежат не в самой кнопке, а в записи её действия**; запись находят по GUID кнопки. Правят их `set_tool_tip`, `set_description`, `set_button_picture`, `set_button_shortcut`. Множества GUID кнопок и записей действий совпадают; расхождение `validate` называет предупреждением уровня 2. Видимый текст кнопки лежит в ней самой (`text`) и с её именем не совпадает.

**Действие бывает четырёх видов** (`ActionSpec`). Два из них записаны тем же узлом, что обработчик события: действие-процедура (`handler` плюс описание) и стандартное действие. У стандартного действия позиция кода названа (`standard_action`). Именами известны пятнадцать кодов из 74 (80 Добавить, 82 Скопировать, …, 142 Закрыть, 300 Справка); имя — транслитерация русской подписи палитры: слова без пробелов, каждое с заглавной буквы, `х` → `h`, `ы`/`й` → `y`, `ю` → `yu`, `я` → `ya`, `ч` → `ch`, мягкий знак не пишется, многоточие отбрасывается. Остальные 59 кодов записываются числом.

**Ссылка на набор кнопок панели — пара «GUID владельца + код»** (`ref_id`, `ref_code`); в карте она встречается в четырёх местах. Этой парой набор называет себя (`ButtonSet.ref_id` и `code`), ею на набор ссылаются, и та же пара стоит внутри описания стандартного действия (`ActionRef` — ссылка на источник действия: у табличных действий она указывает «никуда», у действий формы — на основной набор). Если подменю потеряло свой набор, кнопка остаётся без меню, и `validate` предупреждает на уровне 2.

**Номер кнопки — не её место в списке.** `number` записи кнопки — сквозной номер в порядке создания: кнопка, вставленная перед первой, получает больший номер. Голова блока действий хранит последний выданный номер (`last_number`), а хвост набора перечисляет подменю этими номерами. **Кодек номеров не выдаёт**: добавляя кнопку в JSON вручную, номер ставит человек. Обе связи `validate` проверяет на уровне 2.

**Владелец кнопки — поле `owner`, GUID головы её блока действий:** у кнопки панели — головы блока панели, у пункта меню кнопки формы — головы блока меню. Расхождение — предупреждение уровня 2. **GUID набора (`ButtonSet.ref_id`) берётся из небольшого словаря.** У набора меню кнопки он постоянный: `31946946-0a9b-40a2-95cf-82f200778341` (раздел «Постоянные значения» в `FORMAT.md`). У командной панели это один из четырёх постоянных GUID (`b78f2e80…`, `875faa24…`, `cbcbb11d…`, `206a2abe…`) либо, у подменю панели, GUID головы своего блока. Предупреждения уровня 2: набор панели вне словаря, на который не ссылается кнопка-подменю своего блока; меню без набора или с двумя наборами (у меню набор ровно один); два набора одного блока с одной парой «GUID + код» (ссылки на них неразличимы).

## Целое число как объект, зеркала

**Одно целое число файла может быть в JSON объектом — вид `bits`.** У табличного поля, его колонки, источника данных и поля списка часть свойств собрана в одно число. Карта называет известные биты, а остаток всегда записывается полем `rest`, даже нулевой. Если единица в файле значит «выключено» (`read_only` табличного поля и поля списка, `change_visible` колонки), значение не переворачивается: карта описывает файл. Свойство бывает битом и там, где палитра показывает обычный флажок (ТолькоПросмотр поля списка): вид поля определяет файл.

**Зеркало — одно свойство палитры по двум адресам** (ширина колонки, размер картинки поля картинки, квалификаторы поля ввода, часть флагов поля табличного документа). У второго адреса в карте записана ссылка на первичный. Карта значения не согласует; если они разошлись, `validate` говорит об этом на уровне 2.

## Элементы деревом

**Элементы формы лежат деревом.** Последняя позиция записи элемента (5, а у поля географической схемы и диаграммы — 6) — список вложенных элементов; это тот же узел `Elements`, что у контейнера формы: `{счётчик, элемент…}`. Вложенные элементы бывают у панели и поля табличного документа, у остальных на этом месте `{0}`. Глубина вложенности — до шести уровней. Страницу панели, на которой лежит вложенный элемент, называет поле `page` блока координат. **Имя элемента уникально не везде:** внутри панели имена повторяются, поэтому там `validate` на уровне 2 только предупреждает; повтор индекса — отказ везде.

**Контейнер формы — панель.** Узел `1/2/1` несёт GUID Панели, и его блок содержимого (`LayoutList`) устроен как у панели (`Content.Panel.u1`): голова из двух позиций, шесть счётных списков, семь полей (набор картинок, ОтображениеЗакладок, РаспределятьПоСтраницам, страницы, АвтоПравила, АвтоПорядокОбхода, РежимПрокручиваемыхСтраниц), седьмой список (направляющие), флаг «Исп. только видимую область», по одному числу АктивизироватьПоУмолчанию на каждую страницу и хвост со вторым адресом ЦветаФона. Смещение хвоста зависит от суммы счётчиков, поэтому позиции после списков числом не адресуются: карта называет их `L<n>` (n-й список) и `L<n>+<k>` (позиция через k после конца этого списка), а разбор вычисляет раскладку по файлу. Блок, строение которого не отвечает правилу, записывается без разбора (полем `raw`) с предупреждением уровня 1.

## Блок координат

Блок координат — часть записи элемента с его координатами, привязками и списками зависимых. За головой из двенадцати позиций (метка, четыре координаты, видимость, шесть привязок границ) идут шесть счётных списков зависимых и хвост ровно из пяти позиций. Исключение — блоки с меткой 3: они устроены иначе и записываются без разбора. Длину хвоста карта объявляет (`length=5`); это единственное место, где карта знает длину блока. Хвост из четырёх или шести позиций — отказ: при чтении блок записывается без разбора (у метки 8 это отказ уровня 1), а при записи `encode` называет недостающее поле, иначе именованные поля сдвинулись бы на чужие места.

Тому, кто правит форму вручную, важно следующее:

* страница вложенного элемента — `page`, порядок обхода — `tab_order` (номера от 1 в пределах страницы родителя, пропуски бывают; новому элементу — наибольший плюс один), номер на странице — `page_sequence` (сплошной нумерацией 0…N−1; порядком обхода не является);
* «Ручная привязка» вкладки «Простая» — флаги `manual_anchor_h` и `manual_anchor_v`; привязка, поставленная АвтоПравилами, эти флаги не поднимает;
* **списки зависимых — встречные записи привязок**: `dependents_top` перечисляет элементы, привязанные к верху этого элемента, запись — `{0, индекс элемента, его граница}`; у правила к краю родителя такая запись лежит в списке блока раскладки родителя. **Без встречной записи правило в предприятии не действует, и пересохранение её не дописывает**; конфигуратор пишет встречную запись только к привязке, которую ставит сам. АвтоПравила при записи формы пересчитывают привязки элементов страницы 0 без «Ручной привязки», если на странице менялась геометрия (сдвиг, вставка или копирование элемента; правка свойств пересчёт не запускает); внутри панелей и на других страницах формы пересчёта нет (`docs/anchors.md`). Какое правило выбирается, не выведено; в наблюдённом случае привязка ставится к низу нижнего соседа, смещение равно расстоянию до него, встречная запись — в `dependents_bottom`. Операции редактора ведут встречные записи сами (`docs/anchors.md`), а вручную их пишут вместе с правилом. Висячая ссылка на удалённого соседа — обычное дело, и `validate` о ней молчит;
* пятый и шестой списки всегда пусты: единица на месте счётчика пятого списка — отказ платформы («Ошибка формата потока»), и `validate` отвергает такую форму на уровне 1.

## Данные и ссылки

**Данные привязаны к элементу таблицей, а не полем элемента.** Реквизиты формы лежат в корне (`attributes`), у каждого свой id. Какой элемент к какому реквизиту привязан, говорит `attributes.bindings` — счётный список `{индекс элемента, путь}`. Путь — тоже счётный список, от одного шага до пяти; смысл длинного пути карта не раскрывает (привязка по метаданным — `docs/edit-module-data.md`). `attributes.next_id` — номер следующего реквизита; номера удалённых реквизитов повторно не выдаются. На уровне 2 `validate` проверяет, что привязка называет существующий элемент, id не повторяются и `next_id` не занят.

**Ссылки на элемент бывают двух родов.** Позиция 2 блока заголовка формы — ссылка по индексу; если элемент удалён, платформа сбрасывает её в 4 294 967 295. Висячих ссылок здесь платформа не оставляет, поэтому о такой ссылке `validate` предупреждает на уровне 2. Записи зависимых в блоке координат висячими бывают постоянно, и там проверка молчит. Имени позиции 2 карта не даёт; чаще всего она указывает на командную панель, реже на кнопку.

**Индексы элементов выдаёт счётчик заголовка** — `form.title.last_index`, наибольший выданный номер; после удаления элемента он больше наибольшего индекса. Добавляя элемент вручную, номер берут из счётчика и счётчик увеличивают. Отставший счётчик платформа терпит, поэтому `validate` только предупреждает на уровне 2.

## Варианты строения по скаляру

Вариант строения блока карта выбирает по скаляру. Блок формы бывает двух видов (`kind` 18 — с физическим размером и DPI, 16 — без них), раскладка — четырёх версий (10, 13, 15, 16), общий блок поля ввода — двух (у версии 15 позиция 16 не названа), блок вида значения поля ввода — шести. Вариант виден в JSON по полю, которое его называет; неизвестный вариант записывается целиком без разбора (`raw`). Обычно вариант задаёт первый скаляр блока, и он целый. Исключения: у шрифта вариант задаёт второй скаляр (первый равен 7), а у **типизированного значения скаляр — строка**, буква типа: `{"N",7}` — число, `{"S","alpha"}` — строка, `{"B",0}` — булево, `{"U"}` — значения нет, `{"#",GUID,тело}` — ссылка. Этот узел один для ВыбираемогоЗначения переключателя и обеих колонок строки списка выбора. Буква `D` не разобрана: дата записывается без разбора.

**Список выбора поля выбора — необязательный блок:** он есть в файле, только когда задан, и все следующие позиции сдвигаются на его длину. В карте это счётный отрезок из нуля или одного члена (`choice_list`), хвост адресуется от него (`L1+5`, `L1+6`). Сам список — сериализованный СписокЗначений: колонки «Значение» и «Представление», строки счётным списком, значения типизированные. Второй член отрезка — отказ уровня 2.

**Выпадающее меню кнопки формы — такой же необязательный блок.** Поле `menu_mode` (РежимМеню) принимает три значения. При «Use» и «UseExtra» за головой тела записи лежит блок `menu` — тот же `CommandBarActions`, что у командной панели, — и весь хвост сдвигается на его длину. При «DontUse» ключа `menu` в JSON нет. Хвост при обоих строениях читается теми же ключами: `L1+0`, `L1+1`, `L1+2`, `layout_state`.

## Колонка табличного поля и вложенный элемент

**Колонка несёт вложенный элемент в сжатом конверте.** У колонки один элемент-редактор ячейки (`ЭлементУправления`: поле ввода, флажок или поле выбора). Платформа пишет его строкой `#base64:`: 18 байт постоянного заголовка, raw deflate, длина, BOM и скобочный текст — то же содержимое, что у элемента этого вида на форме. Кодек раскрывает конверт и разбирает тело теми же узлами `Content.<Тип>`. В JSON рядом лежат GUID вида (`control_type`) и сам элемент:

```json
"control_type": {"guid": "381ed624-9217-4e63-85db-c4c3cb87daae"},
"control": {"element": {"content": {"content_kind": 9, "pattern": {…}, "u2": {…}, …},
                        "empty_chunks": 0},
            "links": []}
```

Вид элемента записан в двух местах — в `control_type` и в первом числе тела (`content_kind`: 9 — поле ввода, 1 — флажок, 2 — поле выбора). Если они расходятся, `validate` отвергает форму на уровне 2.

**Колонка списка значений (`fbacf851-…`) вложена на уровень меньше.** Строение колонки (`TableBoxColumn`) выбирается по GUID её вида. У списка, табличной части и таблицы значений колонка записана как `{вид, {4 | 1 | 8, база, Данные…}}` (первое число обёртки — 4, 1 и 8 соответственно); у колонки списка значений обёртки с Данными нет: `{fbacf851-…, база}`. База `{8, голова, ссылка, ссылка, ссылка}` общая; голова — запись с именем, шапкой, шрифтами и вложенным элементом. В JSON у колонки списка значений голова лежит в `u1/u1`, у прочих — в `u1/u1/u1`; ключи те же. Данные этой колонки — ссылки базы `{номер}`, предположительно на поле элемента списка (0 Значение, 1 Представление, 2 Пометка, 3 Картинка; `u2`–`u4` базы безымянны). Вложенный элемент такой колонки правят `set_column_control` и `set_font`/`set_event` с `nested`, шрифты колонки — `set_font` с `column`; Саму колонку заводят и снимают `add_column` и `remove_column` (`docs/edit-columns.md`, раздел «Колонка списка значений»).

**Кодек сжимает так же, как платформа** (штатный zlib, уровень 6). За телом блока бывают k пустых кусков по 27 байт; их число записывается полем `empty_chunks`, смысл их неизвестен. При разборе кодек проверяет, что сборка даёт тот же блок. Если не даёт (например, при другой версии zlib), конверт остаётся строкой: файл по-прежнему собирается байт в байт, но содержимое конверта не разбирается. Исправленный блок собирается тем же сжатием, с тем же заголовком и тем же `empty_chunks`.

Для правки вручную: тело — обычное содержимое элемента, и свойства поля ввода в колонке правятся теми же именами. **Описатель типа (`pattern`) есть только в теле поля ввода**; у флажка и поля выбора его нет, а тип значения колонки лежит у самой колонки (`value_type`). `control_type`, не согласованный с телом, — отказ; вид вложенного элемента меняет `set_column_control`.

## Шрифт

**В файле лежит не сам шрифт, а то, чем он отличается от взятого за основу.** Вид записи задаёт поле `source`: `Auto`, `StyleFont` (шрифт стиля платформы), `SystemFont` (системный шрифт), `Absolute` (все свойства записаны своими позициями). У первых трёх видов за видом идёт маска переопределённых свойств, а за ней — по значению на каждый поднятый бит; поднятый бит соответствует снятой галочке «Из стиля» в диалоге «Выбор шрифта». В JSON маски нет: она определяется набором ключей `overrides`.

```json
{"version": 7, "source": "Auto", "overrides": {"weight": 700, "scale_set": false},
 "L1+0": 1, "scale": 100}
```

* имена свойств одни для всех видов записи и совпадают с именами абсолютного шрифта: `size10` (размер × 10: 100 значит 10), `weight` (400 — обычный, 700 — полужирный), `italic`, `underline`, `strikeout`, `face`;
* порядок ключей `overrides` — порядок значений в файле, и он не совпадает с порядком масок: имя (бит 1) лежит последним, после зачёркивания (бит 32). Разбор раскладывает ключи сам, а `encode` собирает маску по карте, а не по порядку ключей в документе;
* **`scale_set` — булево поле, которое есть всегда:** у бита 512 нет своего значения в файле. Убрать поле нельзя (отказ назовёт его), а `false` снимает бит;
* **масштаб есть только у версии 7:** у версии 6 позиции для него нет. На уровне 2 `validate` отказывает при версии 7 без `scale` и при версии 6 с ним. Правило одно для всех четырёх видов записи (у абсолютного шрифта масштаб — число на позиции 18).

**Где искать шрифт в JSON.** Поле `font` есть у семнадцати типов элементов и у формы; имя одно для всех намеренно — им пользуются смысловой дифф и `set_font`. У некоторых элементов шрифтов несколько: у табличного поля рядом с `font` есть `header_font` и `footer_font`, у колонки — `text_font`, `header_font`, `footer_font`. Всего адресов шрифта двадцать два.

**Что неизвестно.** Хвост записи (`L1+0`, 0 или 1) нигде не виден. Пара «0 плюс GUID» у ссылки на шрифт стиля — вероятно, элемент стиля конфигурации; имени карта не даёт. Номера системных шрифтов, кроме нулевого («Шрифт диалогов и меню»), не проверялись. Имя `scale_set` у бита 512 условное: платформа поднимала этот бит, когда правили только начертание, а масштаб оставался прежним, поэтому «масштаб отличен от обычного» бит не значит.
